# pi_weather_display - known issues & ideas

Running list of things found during development/testing that aren't fixed yet.
Add to this whenever something rough turns up; check items off (don't delete
them) once fixed. Grouped by area, open items first in each group. See also
`docs/settings.md`, `docs/icons.md`, and `docs/changes.md` for the broader
reference docs this list feeds into.

## Icons

- [ ] **`02d`/`02n` icon keys are dead**: `scripts/generate_icons.py` still generates `assets/icons/02d.png`/`02n.png`, and `map_weather_code_to_icon`'s night-remap dict still has entries for them, but the day-mapping side of that function never actually outputs `"02d"` - WMO codes 1/2 map straight to the `022d` composite instead. Either find a real use for these two icons or remove the dead entries/generation. Found while writing `docs/icons.md`.
- [ ] **No hail-specific icon**: WMO thunderstorm-with-hail codes (96/99) share the plain-thunderstorm `11d` icon - only the chart's precipitation axis label (`precip_label`, "Hagel [mm]") distinguishes hail from an ordinary storm; the hourly icon strip does not. Found while writing `docs/icons.md`.
- [ ] **Create dedicated hail icons**: erikflowers/weather-icons has `wi-hail`/`wi-day-hail`/`wi-night-alt-hail` source SVGs (confirmed available, not yet used by `scripts/generate_icons.py`) - add day/night entries (e.g. `96d`/`96n`) the same way the other single-color icons are generated, then map WMO codes 96/99 to them in `map_weather_code_to_icon` instead of falling through to `11d`. Resolves the gap above.
- [ ] **Verify forecast-card moon phase isn't off by one day**: `_parse_forecast()` (`weather_data.py`) computes each forecast card's moon phase for `target_date = dt.date() + timedelta(days=1)` - one day ahead of the card's own date. Presumably intentional (matching "phase for the night that date's forecast covers") but never explicitly verified against a real calendar/reference. Found while writing `docs/icons.md`.
- [ ] 71d/73d/77d (light/moderate snow/snow-grains) all render as the exact same icon (`wi-day-snow`) - weather-icons doesn't have graduated snow-intensity variants the way the old per-condition Flaticon set implied. Similarly 51d/53d/09d (light/moderate/heavy rain) use different source icons but look very similar at small render sizes. Not wrong, just less differentiated than before.
- [ ] `wi-night-clear` (icon `01n`) renders as a noticeably thinner/paler crescent than the `wi-moon-*` family used for moon phases - same fill color, different path weight in the source SVG. Cosmetic only.

## Fonts & text

- [x] **Chart gridline-mode max-value label can collide with the topmost tick label** (2026-08-12, branch `todo-fonts-wifi-fixes`, built while away): fixed - the gridline loop now skips any tick within one label-height of the max/min axis-extreme label (measured via `font_bold.getbbox()`, not a guessed pixel constant), not just an *exact* value coincidence like before. Verified against the original Ulaanbaatar repro case and the full 14-location suite.
- [x] **Missing font glyph fallback** (2026-08-12, branch `todo-fonts-wifi-fixes`, built while away): fixed - new `AssetStore.fallback_font()`/`draw_text_with_fallback()` (`widgets/icons.py`) fall back to a new bundled Noto Sans JP (broad combined Latin/Cyrillic/Greek/CJK coverage) per-character when the active family (Jost/Bitter) has no real glyph for it, wired into `canvas.py`'s header (the only call site that draws unpredictable API-sourced text). Glyph-coverage detection has no direct PIL/FreeType API and needed a small trick: comparing a character's `getbbox()` against a probe codepoint (`U+E000`, guaranteed absent from any real font) that reveals each font's own shared `.notdef` glyph "fingerprint" - avoids adding a cmap-parsing dependency. Verified against the actual originally-reported Tokyo case (`杉並区, Japan`) via the standing 14-location suite, through the real quantization pipeline. Complex-script languages (Arabic/Thai/Devanagari/Hebrew) would still render with correct glyphs but wrong shaping/ordering - Pillow's `text()` has no bidi/shaping engine - a real, separate limitation not solved here.

## WiFi & web UI

- [x] **No SSID rename** (2026-08-12, branch `todo-fonts-wifi-fixes`, built while away): fixed - `wifi_manager.edit_network()` takes an optional `new_ssid`, renaming the connection profile and its actual broadcast SSID together in one `nmcli connection modify` (add_network always kept these equal already) - no remove + re-add needed. Along the way, made the existing password field independently optional too (previously any edit submission always touched the password, even blank).
- [x] **No periodic reconnect check** (2026-08-12, branch `todo-fonts-wifi-fixes`, built while away): implemented - a new background daemon thread in `web_app.py` (`_periodic_reconnect_check`) checks connectivity every 60s, falling back to the setup AP after 3 consecutive failed checks (debounced so a momentary router blip doesn't flip the panel into AP mode). This reverses the original v1 "Phase 8, deliberately out of scope" deferral - worth confirming that's actually wanted now, not just built because it was on the list.
- [x] **No real captive-portal DNS redirect** (2026-08-12, branch `todo-fonts-wifi-fixes`, built while away): implemented - `wifi_manager._write_dnsmasq_ap_config()` now adds `address=/#/<AP_IP>` (wildcard DNS), so any domain resolves to the device while the setup AP is active. Only DNS-level, not a full captive-portal (no 802.11u "sign in to network" OS popup, HTTPS requests will fail TLS validation against the device's IP) - enough for a manually-opened plain HTTP URL, which is what the existing setup screen already tells people to do.
- [ ] **No authentication anywhere in the web UI** - **deliberately left untouched** even though the rest of this section was worked while away - this one reverses an explicit, documented design decision (trusted-LAN-only threat model, matches button A's own unauthenticated physical shutdown), not a gap to close, so it needs an explicit yes/no rather than being unilaterally added. Still deliberate, matches button A's existing unauthenticated physical shutdown and the project's trusted-LAN-only threat model - documented explicitly in `docs/networking.md`, not an oversight, but would need revisiting if this device is ever exposed beyond a home LAN.
- [x] **No QR code on the setup screen** (2026-08-12, branch `todo-fonts-wifi-fixes`, built while away): implemented - new `qrcode` dependency, `setup_screen.py` now renders a `WIFI:S:...;T:WPA;P:...;;` QR code (phones' native camera apps recognize this for one-tap joining) alongside the existing text instructions, in a redesigned two-column layout. Verified it survives the panel's hard quantization pipeline (QR modules are already pure black/white, no antialiasing to harden) and that module size (~1.2mm at this panel's ~127 PPI) is in the normal scannable range - **not verified with an actual phone scan**, only computed/simulated; worth confirming in person.

## Display & hardware

- [x] **Button A's blank-before-shutdown screen quantized at the wrong saturation** (2026-08-12, branch `todo-fonts-wifi-fixes`, built while away): `button_listener.py`'s `blank_and_shutdown()` called `InkyDriver()` with no `saturation` argument, always using the class's hardcoded default (`0.5`) instead of whatever `inky_saturation` is actually configured (default `0.0`) - the blank screen was quantized differently from every other screen the app ever shows. Fixed: reads `settings_store.load_config().inky_saturation` first, same pattern already used correctly in `main.py`/`web_app.py`.
- [ ] **Blank-before-shutdown screen has a mild sprinkling of black dots on real hardware, not just solid white** - investigated (2026-08-12): rendered a synthetic pure-white image through the exact same `quantize_for_panel()` pipeline `blank_and_shutdown()` uses, at both `saturation=0.5` (the old hardcoded bug above) and `0.0` (the real configured default) - both produced a perfectly uniform single-color output, zero stray pixels. Rules out the software quantization pipeline as the cause. Very likely a genuine physical e-paper artifact (incomplete ink-particle clearing/ghosting from the previous image - a known characteristic of multi-color ACeP panels, especially since this screen doesn't do a full clear cycle first) rather than a software bug. Not fixed - would need a real clear-cycle before showing blank, a bigger and riskier hardware-level change than investigated here.
